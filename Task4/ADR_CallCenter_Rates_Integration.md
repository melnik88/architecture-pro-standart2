### **Название задачи:** Интеграция кол-центров с системой управления ставками депозитов

### **Функциональные требования**
Опишите здесь верхнеуровневые Use Cases. Их нужно оформить в виде таблицы с пошаговым описанием:

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
|1|Сотрудник кол-центра банка|Консультация по актуальным ставкам депозитов|1. Клиент звонит в кол-центр с вопросом о ставках<br>2. Сотрудник открывает систему кол-центра<br>3. Система отображает актуальные ставки по всем депозитным продуктам<br>4. Сотрудник консультирует клиента по условиям|
|2|Сотрудник партнёрского кол-центра|Консультация по актуальным ставкам депозитов|1. Клиент звонит в партнёрский кол-центр<br>2. Сотрудник открывает внешнюю систему партнёра<br>3. Система отображает актуальные ставки из полученного файла<br>4. Сотрудник консультирует клиента по условиям|
|3|Rate Management Service|Обновление ставок в кол-центрах|1. Сотрудник отдела кредитования обновляет ставки в Rate Management Service<br>2. Система автоматически передаёт обновления в систему кол-центра банка через API<br>3. Система формирует файл со ставками для партнёрского кол-центра<br>4. Файл передаётся по SFTP в систему партнёра|
|4|Менеджер бэк-офиса депозитов|Управление ставками депозитов|1. Менеджер работает с ставками через интерфейс Rate Management Service<br>2. Система валидирует данные и обеспечивает консистентность<br>3. Ставки автоматически распространяются во все подключённые системы<br>4. Кол-центры получают обновления в реальном времени|

### **Нефункциональные требования**
Опишите здесь нефункциональные требования и архитектурно значимые требования.

|**№**|**Требование**|
| :-: | :- |
|1|**Доступность Rate Management Service**: Сервис должен быть доступен в рабочие часы кол-центров (8:00-20:00) с uptime 99%|
|2|**Производительность интеграции**: Обновление ставок в кол-центрах должно происходить в течение 5 минут после изменения в Rate Management Service|
|3|**Безопасность передачи данных**: API-интеграции должны использовать HTTPS, SFTP-передачи должны быть зашифрованы|
|4|**Интеграционные возможности**: Rate Management Service должен поддерживать REST API для кол-центра банка и SFTP для партнёрского кол-центра|
|5|**Совместимость с существующими системами**: Использование технологий, уже применяемых в Rate Management Service (PostgreSQL, Java Spring Boot)|
|6|**Обработка сбоев**: При недоступности Rate Management Service кол-центры должны информировать клиентов о технических проблемах и невозможности предоставить актуальные ставки|

### **Решение**
Предлагается расширить уже спроектированный **Rate Management Service** для поддержки кол-центров с полной инкапсуляцией функциональности внутри сервиса:

**1. Расширение существующего Rate Management Service:**

- **Дополнительные API endpoints для кол-центров**
  - GET /api/rates/deposits - получение актуальных ставок по депозитам
  - GET /api/rates/deposits/personalized/{clientId} - персонализированные ставки

- **SFTP-модуль для партнёрского кол-центра**
  - Автоматическое формирование файлов со ставками в формате CSV/XML
  - Планировщик для регулярной отправки файлов по SFTP
  - Встроенное логирование и мониторинг передачи файлов

- **Встроенный мониторинг и метрики**
  - Spring Actuator endpoints для health checks
  - Кастомные метрики для API кол-центров (время отклика, количество запросов)
  - Логирование и метрики SFTP-операций
  - Интеграция с Prometheus/Grafana

- **Оптимизация производительности и кэширование**
  - Анализ и оптимизация запросов к PostgreSQL
  - Настройка connection pooling для базы данных
  - **Кэширование актуальных ставок:**
    - Кэширование ставок с TTL для быстрого отклика кол-центрам
    - Cache invalidation при обновлении ставок в базе данных
  - Асинхронная обработка SFTP-операций

- **Конфигурация SFTP-интеграций**
  - Настройка SFTP-клиентов для разных партнёров
  - Управление форматами экспорта (CSV/XML)
  - Retry механизмы для неуспешных передач
  - Валидация и обработка ошибок

**2. Модификации существующих систем:**

- **Система кол-центра банка**: добавление модуля отображения ставок через API
- **Система партнёрского кол-центра**: настройка импорта файлов со ставками по SFTP

**Архитектурные преимущества:**
- Использование уже спроектированного и протестированного Rate Management Service
- Единый источник ставок для всех каналов (сайт, интернет-банк, кол-центры)
- **Инкапсуляция всей функциональности внутри одного сервиса** - упрощение архитектуры
- **Самодостаточность сервиса** - минимизация внешних зависимостей
- **Единая команда разработки** - лучшее качество и скорость разработки

**Логика принятия решений:**
- Повторное использование уже спроектированного Rate Management Service
- Использование стандартных протоколов: REST API для внутренних систем, SFTP для внешних партнёров
- Сохранение единого источника истины для ставок депозитов
- **Следование принципам микросервисной архитектуры** - сервис отвечает за все аспекты своей функциональности
- **Использование встроенных возможностей Spring Boot** для мониторинга и метрик


### **Альтернативы**

**Альтернатива 1: Прямая интеграция кол-центров с АБС**
- Преимущества: Простота реализации, использование существующих интеграций
- Недостатки: Дополнительная нагрузка на АБС, сложность масштабирования, отсутствие централизованного управления

**Альтернатива 2: Создание отдельного сервиса интеграции с кол-центрами**
- Преимущества: Разделение ответственности, специализированная функциональность
- Недостатки: Дублирование логики управления ставками, дополнительная сложность архитектуры, необходимость синхронизации данных

**Альтернатива 3: Выделение инфраструктурных задач в отдельные команды**
- Преимущества: Разделение ответственности между командами
- Недостатки: Усложнение координации, размытие ответственности, увеличение времени разработки, дублирование экспертизы

**Альтернатива 4: Ручная передача ставок через email**
- Преимущества: Минимальные технические изменения
- Недостатки: Высокий риск ошибок, задержки в обновлении, отсутствие автоматизации

**Недостатки, ограничения, риски**

**Недостатки выбранного решения:**
- Увеличение сложности Rate Management Service
- Зависимость кол-центров от централизованной системы

**Ограничения:**
- Партнёрский кол-центр может принимать данные только через SFTP
- Необходимость обучения сотрудников работе с новой системой
- Ограничения по производительности при большом количестве одновременных запросов (минимизированы за счет встроенной оптимизации)

**Риски и меры по их снижению:**
- **Риск недоступности централизованной системы** → Встроенный мониторинг и health checks, быстрое обнаружение проблем
- **Риск задержек в обновлении ставок** → Асинхронная обработка SFTP-операций, retry механизмы
- **Риск несовместимости с системами партнёров** → Гибкая конфигурация форматов экспорта, валидация данных
- **Риск превышения бюджета** → Сокращен за счет концентрации задач в одной команде (с 2.5-3 до 2-2.5 месяцев)
- **Риск увеличения времени разработки** → Минимизирован за счет устранения координационных задач между командами
